## 二、当前出厂默认的分阶段耗时

一轮 44.76s 的构成：

| 阶段 | 秒 | 占比 | 说明 |
|---|---|---|---|
| `fetch` | 16.57 | 37% | 5 个源并发抓取；每源先试直连（GitHub 被墙，固定烧 15s）再回退 jsDelivr |
| `prepare` | 0.03 | 0.07% | 解析/合并/抽样，1 万条候选也只要几十毫秒 |
| `tcp` | 11.26 | 25% | 300 并发，超时 2s |
| `tg` | 16.87 | 38% | 100 并发；第一关按门槛派生 2s，第二关固定 8s |
| `commit` | 0.02 | 0.05% | 聚合 + 落盘（原子写） |

**`fetch` 现在是最大单块，且是环境成本**（GitHub 被墙），不是算法问题。
要动它只能做镜像竞速（P3），且必须先定义「完整响应」的判据。

## 三、关键参数与推导关系

```
TCP 预筛超时   = max(2.0, max_tg_latency_ms/1000 + 1.0)      # tcp_timeout_for
TG 第一关预算  = max(2.0, max_tg_latency_ms/1000 + 1.0)      # tg_dc_timeout_for
TG 第二关预算  = 8.0                                          # 与门槛无关
单节点总预算   = max(20, dc + web + 2)                        # tg_deadline_for
TCP 并发       = 300                                          # TEST_MAX_WORKERS
TG  并发       = 100                                          # TG_TEST_MAX_WORKERS
```

**为什么 TCP 预筛和 TG 第一关都要跟门槛耦合**：`tg_latency` 从 `create_connection`
起算，包含到代理的握手；握手超过门槛的节点必然被剔除。所以这两处超时必须
≥ 门槛 + 余量，否则「能过门槛」的节点会被提前砍掉。

**为什么第二关不跟门槛耦合**：第二关是 TLS 握手 + HTTP 往返，实测
`web_p50` 就有 2~3 秒、`p90` 到 8 秒。用 2s 会砍掉一半以上。

## 四、剪枝规则（等价变换，不是估算）

```
if dc_ms > max_tg_latency_ms:   # dc_ms 就是最终的 tg_latency
    跳过第二关，返回 dc_ms
```

**剪枝时返回 `dc_ms` 而不是 `None`**：让下游把它当成「过了两关但超门槛」，
从而 `tg_failed` 计数、`kept` 排除、「通过则清零连败」三者语义保持不变。
若返回 `None`，会被当成失败累计连败，三轮后误拉黑。

实测效果：`ok` 从 86/54 降到 11/13，**正好等于 `available`** —— 语义变干净了。

## 五、可用的度量字段

`GET /api/proxies` 新增三个字段（均与 `stats` 平级）：

| 字段 | 内容 |
|---|---|
| `stage_durations` | `{fetch, prepare, tcp, tg, commit, total}`，单位秒 |
| `tg_gate_stats` | 两关分布：`dc_fail` / `latency_rejected` / `web_fail` / `ok` 的计数与分位 |
| `stats` | 原有 6 个计数（未变） |

`GET /api/version` 返回 `{app, version}`，用于确认跑的是哪个构建。

## 六、环境变量（A/B 与回退用）

| 变量 | 默认 | 用途 |
|---|---|---|
| `TGPROXY_TCP_TIMEOUT` | 2.0 | TCP 预筛超时的**下限** |
| `TGPROXY_TCP_WORKERS` | 300 | TCP 并发；若发现被代理站点限流可回退 150 |
| `TGPROXY_TG_DC_TIMEOUT` | 2.0 | TG 第一关预算的下限 |
| `TGPROXY_TG_TIMEOUT` | 8.0 | TG 第二关预算 |
| `TGPROXY_TG_DEADLINE` | 20.0 | 单节点总预算的**下限** |
| `TGPROXY_FETCH_TIMEOUT` | 15 | 抓取超时 |

**注意**：超时类的三个（TCP / TG DC / TG DEADLINE）都只是**下限**，
实际值会按延迟门槛派生。调低它们不会突破「预算 ≥ 门槛」的约束。

## 七、复现方式

```bash
# 1. 构建
cd tgproxy && pyinstaller tgproxy.spec

# 2. 采集（3 轮，独立数据目录，自动杀进程树）
python measure.py dist/tgproxy.exe <工作目录> 3 <输出.json> <标签>

# 3. A/B（同一二进制，只改环境变量）
TGPROXY_TCP_WORKERS=150 python measure.py ...
```

`measure.py` 的三个要点（都踩过坑）：端口靠探测而非解析 stdout、每个 build
独立目录（`BASE_DIR = dirname(exe)`，`known_good.json` 不会互相喂）、
开跑前清空四个运行期文件。

## 八、不要再犯的测量错误

1. **绝对耗时跨轮不可比** —— 候选池每轮都在漂（`random.sample` 未 seed），
   测数能从 1300 变到 2700。要比就比 `ms/节点`，或者比同构池子。
2. **`ms/节点` 也不是万能的** —— 它只抹平「测多少条」，抹不平「死节点占比」。
   死节点多的时候单位耗时天然更低（每个更快失败）。跨臂比较要看 `dropped` 占比。
3. **任何「开关没效果」的结论，先做阳性对照** —— 曾经因为 exe 比 env 支持还早，
   把「变量没生效」误读成「降超时无效」。用极端值（如 0.01s）跑一轮证明通路。
4. **构建后要核对产物内容** —— PYZ 是 zlib 压缩，二进制 grep 查不到字符串；
   字典字面量的键在 tuple 常量里（`BUILD_CONST_KEY_MAP`），不在 `co_consts` 的字符串里。
